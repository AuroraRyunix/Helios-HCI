# Helios-HCI Roadmap & Technical Debt

This is a living backlog. Items are pulled from [docs/audit_findings.md](./docs/audit_findings.md) (verified against current code — many findings in that document have already been fixed since it was written; only genuinely open items are listed below) and [docs/add_ons_design.md](./docs/add_ons_design.md) (designed but not yet implemented). See [docs/history/walkthrough.md](./docs/history/walkthrough.md) for the record of what has already been fixed.

## 1. Known Architectural Gaps (from docs/audit_findings.md)

These are open as of the current code (verified by reading the referenced files; items from the audit that turned out to already be fixed — e.g. the ZooKeeper Observer split, Daruk's `ConsistencyLevel.ONE` fallback, Bifrost's dynamic subnet-prefix detection, Gatoway's per-line default-route parsing, the Mipha DRBD split-brain ZK tie-breaker, the Vali parallel DRS polling/storage-capacity gates/migration lock, the Spark service watchdog, Daruk's connection retry loop, Urbosa's dynamic uplink interface, VNC `TCP_NODELAY`, and all of the Lanayru guest-K8s provisioning bugs — are intentionally **not** repeated here).

* **Bifrost split-brain VIP conflict** (`bifrost.py`, `get_zookeeper_leader_ip`): if ZooKeeper consensus is lost, Bifrost falls back to `candidates.sort(); return candidates[0]` over any host with an open Slate/Spectrum port, rather than releasing the VIP. In a network partition, both sides of a 2-node cluster can independently decide they own the VIP, causing MAC/routing conflicts.
* **No out-of-band fencing path** (`mipha.py` `ssh_fence_host`): host fencing relies entirely on Spark's mTLS execute API (port 9099). If a node's software has hung but the box is still powered on, there is no passwordless-SSH or IPMI/PDU STONITH fallback, so Vali can end up starting VMs on a healthy node while the "dead" node is still running them (dual-primary disk corruption risk).
* **No mTLS certificate renewal**: Spark's CA/node/client certificates under `/etc/hci/spark/certs/` and `/root/.certs/` are generated once at provision time with a fixed lifetime; there is no renewal daemon or cron job. Expiry silently freezes all inter-node orchestration.
* **Unsandboxed root command execution** (`spark_daemon_decoded.py`, `/api/v1/execute`): command strings from callers are still executed via `subprocess.Popen(..., shell=True)`/`subprocess.run(..., shell=True)` as root, with no whitelist or parameterized wrapper. Any injection bug upstream (Spectrum's web API, Vali's scheduler) escalates directly to root on every hypervisor.
* **Catalyst/Vali internal APIs are reachable on the LAN with no auth** (not in `docs/audit_findings.md`, found while verifying the README's network claims): both `catalyst.py` (port `9091`) and `vali.py` (port `9095`) run in Quadlet containers with `Network=host` and call `ThreadingHTTPServer(("0.0.0.0", <port>), ...)` directly — contrary to the previous README wording, they are not restricted to loopback, and neither handler checks the caller's source IP or requires a credential. Anyone who can reach the cluster network can submit/query orchestration tasks.
* **No maintenance-mode quorum gate** (`vali.py` host-maintenance handling): entering maintenance stops the local `hydra-db` (ScyllaDB) container unconditionally. On a 1- or 2-node cluster, with `ConsistencyLevel.QUORUM` as the default, this can freeze all database queries cluster-wide; there's no active-node-count gate before allowing maintenance entry, and no ScyllaDB ring decommission/rejoin sequencing for long-running maintenance.
* **Referenced but missing storage auto-heal script**: `spectrum_server.py` registers a daily Dagur cron task (`storage_auto_heal`) that invokes `/usr/local/bin/hci-auto-heal` — this script does not exist anywhere in the repository, so the scheduled task will fail every time it runs. Either implement `hci-auto-heal` or remove the dangling cron registration.
* **No backup / disaster-recovery manager**: there is no service that periodically snapshots the ScyllaDB `hydra` keyspace or Linstor configuration metadata to an external target (NFS/S3/etc). A corrupted DB or wiped DRBD metadata is currently unrecoverable.
* **No automated host self-fencing / quarantine on partial failure**: if a host's storage or database daemon crashes while the OS/network/SSH stay up, Mipha's ping-based liveness check still reports it healthy, so no failover is triggered and VMs on that host can remain stuck in a broken state indefinitely.
* **Proposed Mimir/mcli diagnostic checks not implemented**: none of the diagnostic check IDs proposed in `docs/audit_findings.md` §13 (`zookeeper_ring_scale`, `scylladb_quorum_safety`, `mtls_cert_expiry_warning`, `fencing_access_check`, `watchdog_daemon_status`, `drbd_split_brain_check`, `linstor_latency_check`, `drs_storage_capacity_check`, `migration_lock_status`) exist in `mimir.py`, `mcli`, or `mcli-runner` yet.
* **Air-gap / private registry hardcoding** (`provision.py`): container images for ScyllaDB, ZooKeeper, Linstor, and Traefik are hardcoded to `docker.io`/`quay.io`. There's no `--registry` flag or config variable to prefix a local mirror, which blocks provisioning in air-gapped datacenters.
* **VXLAN head-end replication overhead** (`urbosa.py`): the SDN overlay still populates VXLAN FDBs with static flood entries (`bridge fdb append 00:00:00:00:00:00 ... dst <peer>`) rather than a control-plane-driven ARP suppression table, so every broadcast/multicast packet is replicated to every peer node. This gets expensive at scale (see "Scale-Out Urbosa" below, which is the designed fix).

## 2. Missing Tooling / Process

* **No top-level `LICENSE` file.** The project has no declared license.
* **Vendored frontend libraries lack bundled attribution.** `static/novnc/` source files declare `Licensed under MPL 2.0 (see LICENSE.txt)` in their headers (e.g. `static/novnc/rfb.js`), but no `LICENSE.txt` is actually bundled anywhere under `static/novnc/` in this repo. `static/vendor/pako/` carries no license header or file at all. Both need their upstream license text added. (`static/spice-html5/` is fine by comparison — its `COPYING`/`COPYING.LESSER` are present.)
* **No CI/CD.** There is no `.github/workflows` directory — no automated linting, no `test_hylia.py` run on push/PR, no build validation of `agahnim` (Rust) or the Dockerfile. All verification is manual today (see [docs/setup-guide.md](./docs/setup-guide.md)).
* **No `requirements.txt` / dependency pinning.** All root Python scripts assume their third-party dependencies (`paramiko`, `cassandra-driver`, etc.) are already present on the EL10.2 host image. Nothing in-repo pins versions, so a fresh dev machine has no reliable way to install matching dependencies.

## 3. Design / Future Work (from docs/add_ons_design.md)

None of the following four scale-out add-ons have any implementation in the repo yet — they exist only as architectural blueprints:

* **Helios Portal** — a multi-cluster management control plane (Prism Central analog): aggregation service, federated Prometheus metrics, federated Loki logs, cross-cluster Hylia LCM staging.
* **Helios Files** — a scale-out NFS/SMB file server add-on backed by a Linstor/DRBD HA block volume, orchestrated by Vali with Mipha-driven failover.
* **Helios Horizon** — an Active Directory-integrated VDI/application-streaming system using Apache Guacamole (`guacd`) to bridge RDP to HTML5/WebSockets, with an applications-only web portal mode.
* **Scale-Out Urbosa** — replaces Urbosa's current static VXLAN FDB flooding with an FRRouting-based BGP EVPN control plane and per-host ARP suppression tables, directly resolving the head-end-replication gap listed above.
